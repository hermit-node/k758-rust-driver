# K758 investigation: experiments, proof, failures, and open questions

**Evidence ledger last updated 2026-10-20.** This document reports **our own K758 testing**; it does not claim that a feature in another Redragon model works here. For upstream options and next-step design, see [README_REFERENCE_IMPLEMENTATIONS.md](README_REFERENCE_IMPLEMENTATIONS.md). For reusable protocol detail, see [docs/PROTOCOL_NOTES.md](docs/PROTOCOL_NOTES.md).

## Status at a glance

| Independently read actual stored macro program | **Not implemented / not verified** | We have historical OEM `0x0A` upload payloads and preserved W macro **reference** only |

| Firmware macro with arbitrary vendor HID / custom KHID output | **Not verified** | Macro storage and accepted output types remain unknown |

## Background: do not confuse the three levels

- **Physical key**: the switch on the K758; our goal is an independent, stable KHID identity for it.
- **Firmware assignment**: a 3-byte entry such as `02 02 04` (keyboard A), `02 02 07` (keyboard D), or `05 01 00` (W's macro reference). Firmware interprets this before Windows receives the keyboard output.
- **Windows input / VK**: the keyboard output (possibly already remapped by firmware) as observed by Raw Input. A Windows VK of A does **not** prove the physical A key was pressed.

A KHID event is generated by **our software** only once the physical source is authenticated. We have not established a native K758 firmware KHID report.

## Experiments, in approximate chronological order

### 1. Independent Studio GUI and read-only diagnostics

An independent Windows/PySide6 K758 Studio was made with a 39-key keypad view, four **local editing banks**, local macro library/drafts and simulated RGB. Its initial Save to Device was **disabled**; most GUI functionality was previews, not onboard configuration.

A borrowed Rust Raw Input diagnostic observed the separate Windows keyboard interface `MI_00` and vendor `MI_01 / Col04`. Early evidence: the physical D key generated Windows A because of its stored mapping. This was evidence of a **firmware remap already in effect**, not a physical D-to-KHID edge decoder.

**Limitation identified:** separate on-screen editor bank selections could become out of sync with the actual hardware M1-M4 bank.

### 2. Hardware profile reporting, F9 through F12

A read-only 2026-10-20 capture showed:
- F9, keyboard scan `0x43`, vendor status byte `00` -> M1
- F10, scan `0x44`, vendor status byte `01` -> M2
- F11, scan `0x57`, vendor status byte `02` -> M3
- F12, scan `0x58`, vendor status byte `03` -> M4

A vendor response included header `04 2F 00 03 2C ...` with device identity data and active bank at **report index 18** (zero-based), followed by `18` at index 19. Mode reports can repeat; reports from unrelated command families are not automatically profile changes.

The independent Studio fork added **read-only auto-follow** of M1-M4 status, with an opt-out. Recorded sessions were replayed offline and passed GUI tests, including M4 capture. This **did not** write profiles or implement software KHID remapping.

Evidence files remain local, under the separate Studio investigation project:
- `PROFILE_SYNC_EVIDENCE.md`
- `M4_CAPTURE_EVIDENCE.md`

Their detailed raw input JSONL captures were intentionally **not added to this public repository**.

### 3. OEM captures, exact K758 configuration packets

OEM `K758RGB.exe` transactions were captured while configuring profiles. In particular, we had a historical M1 Apply image that includes the current-at-capture W macro assignment and physical D assigned to A.

A complete OEM M1 Apply transaction consists of **nine 64-byte reports**, in this order:

| Step | Command | Observation |
|---|---|---|
| 1 | `0x01` | Begin transaction |
| 2 | `0x0A` | Macro-related payload part 1 |
| 3 | `0x0A` | Macro-related payload part 2 |
| 4 | `0x06` | Profile parameters |
| 5-8 | `0x08`, four times | Four stored keymap pages |
| 9 | `0x02` | End transaction |

**Important:** from two macro-related OEM upload packets alone, we have **not** established a general macro read command, macro slot format, timing units, or the device's nonvolatile memory address. `0x0A` is a firmware configuration **write** family; it is not itself what Windows sees when a macro runs.

The packaged historical fixture is `fixtures/m1_D_A_to_D_PREVIEW_only.json`. It includes actual captured macro bytes; the file is currently part of a **public** GitHub repository. Do not add raw typed-character logs or other new captures without a separate privacy review.

### 4. Read-only active map: `0x0F` initially misled us

Early reads from `0x0F` looked like normal default assignments: D -> D and W -> W, even though the actual active firmware settings included D -> A and W -> macro.

This **was not proof** that the active profile had been restored or that the wrong profile had been selected.

We then used K758 `0x07` with four requests: offsets/lengths `0x0000/56`, `0x0038/56`, `0x0070/56`, `0x00A8/24`. The returned concatenated 192-byte keymap **matched the historical OEM M1 image byte-for-byte**. This resolved which command returned M1's actually customized mapping.

**Result:** `0x07` is the verified K758 active-custom-map read method for the tested unit. `0x0F` returns a different, default-looking view, but the exact semantics of that view are unproven. The K586 HIDra implementation reports the opposite assignments for these command names on **another keyboard**. Model-specific behavior wins over naming conventions.

### 5. Packet format, replies and transport experiments

On the K758's 64-byte report ID `04`:
- outgoing checksum is a little-endian 16-bit sum of packet bytes **3 through 63**;
- a `read_timeout` reply preserves the **request's header and original checksum**, even though its data payload is different;
- validating a reply checksum by summing the **reply** payload would falsely reject valid data;
- correct reply validation checks report length, echoed request fields/header, expected command/response and device.

**Unsuccessful approach:** earlier Win32 `HidD_SetOutputReport` / direct `WriteFile` output methods did **not** yield a successful verified configuration transaction in our trial. They should not be claimed compatible merely because the API exists.

**Successful approach:** Rust `hidapi::HidDevice::write(&[u8;64])` on the **identified vendor interface**, followed by `read_timeout` for matching acknowledgments, worked on the hardware. The Redragon OEM application must be fully closed to avoid transport conflicts.

### 6. Active bank selection and lighting audit

An exact OEM-captured `0x04` M1 select packet was transmitted on a test that began on M2. A `0x03` query independently confirmed the hardware was now M1.

This is an **actual hardware state change**, not a mere selection in the GUI. It must remain opt-in, not an automatic side effect of opening the driver.

The `0x05` command read four 56-byte lighting blocks at addresses `0x00`, `0x40`, `0x80` and `0xC0`. Their first values were `07`, `04`, `08` and `07`, and the blocks differed. **These four read addresses are lighting data offsets; do not confuse them with hardware M1-M4 selectors.**

### 7. M1 D assignment restore, 2026-10-20

**Preconditions checked:** Redragon software closed; exactly one matching HID vendor collection; active bank M1; complete **192-byte** active M1 readback exactly matches the historical OEM M1 image. Private prewrite evidence was saved.

The prewrite relevant 3-byte keymap slots:
- **physical D**: map bytes 84..86 = `02 02 04`, so output A;
- **physical W**: bytes 57..59 = `05 01 00`, a macro reference.

Only **two packet bytes** differ between the historical nine-frame M1 image and the desired transaction:
- report 6 (one-based), byte index **38** (zero-based): `04 -> 07` (A HID usage to D HID usage);
- same report, byte index **1**: checksum `7A -> 7D`.

Nine write packets were sent with `hidapi.write`, each followed by a matching command acknowledgment. A fresh independent Rust audit after the writer exited then re-read `0x07` across all 192 bytes.

**Verified post-write comparison:**
- exactly **one** of the 192 keymap bytes changed (absolute offset **86**, `04 -> 07`);
- D's stored entry became `02 02 07`;
- W's keymap macro reference remained `05 01 00`;
- every other mapping byte was unchanged;
- all **four lighting blocks** were unchanged;
- bank M1 remained selected.

**Do not overstate this result:** it proves successful firmware configuration + independent stored-state verification. The **actual** macro program was re-uploaded as historical captured data; we did *not* independently read it from the device before/after. W macro behavior and physical D keypress still require user validation.

Sanitized, published evidence: [docs/M1_WRITE_VERIFICATION.json](docs/M1_WRITE_VERIFICATION.json). The original, richer before/after evidence snapshots remain **only on the authorized local machine**, in the K758 Studio `investigation` folder:
- `m1_prewrite_verified_20261020-181926.json`
- `m1_postwrite_verified_20261020-182026.json`

Do not delete those files, overwrite them, or replace them with a newer machine state without the user's approval.

### 8. Independent, buildable Rust package

The K758-only repository was split into its own Rust Cargo project:
- `src/main.rs`: full OEM-captured M1 transaction, exact preflight, dry run, apply, and `--verify-restored` read-only verification.
- `src/bin/k758_profile_audit.rs`: profile + lighting + two keymap command readbacks; `--preview-select-m1` and an explicit `--select-m1` hardware selector.
- `fixtures/m1_D_A_to_D_PREVIEW_only.json`: exact M1 original/proposed packet frames.

On 2026-10-20, `cargo test --release` passed **four tests**, and `cargo build --release` succeeded. The packaged `--dry-run` was successful with no USB writes. The packaged `--verify-restored` binary subsequently read live M1 successfully:

```text
HARDWARE_PROFILE=M1
MAP_LENGTH read=192 expected=192
PHYSICAL_D_ENTRY 02 02 07
RESTORATION_VERIFIED full_keymap=192/192 D=02_02_07 W_macro=05_01_00 configuration_writes=0
```

Source committed to [hermit-node/k758-rust-driver](https://github.com/hermit-node/k758-rust-driver), initially at `bf7299927fb5fa01a4930b414bc1d6019f967032`. The local Git repository was subsequently aligned to the uploaded remote, with the initial local commit retained on a backup branch.

**Present limitation:** two binaries still duplicate packet construction and read code; `make_query` builds a request, `query` sends one and validates the response. Their distinct responsibilities are sound, but their **duplicate implementations** should merge into one library before expanding functionality. No general M1-M4 write engine or arbitrary keymap editor has yet been added.

## What we have *not* tried or proved

### Runtime keypress identity (critical next test)

The read-only Studio captures show keyboard outputs and vendor **profile status**, but no evidence yet establishes that pressing every ordinary K758 key produces its own unique vendor-defined input report. Some programmable keyboards (notably a K596 project) can report G-key presses separately; **that behavior has NOT been confirmed on K758**.

The W key's `05 01 00` reference is an **internal firmware keymap field**, **not** a Windows key event and **not** a KHID ID. Windows may only receive the macro's replayed standard keyboard events. Do not assume the firmware sends a vendor notification each time a macro executes.

A Windows `WM_INPUT` listener that reports K758 keyboard-originated `VK_A` cannot prove which physical key generated that output if multiple switches share it. Windows Raw Input observes input; it does **not** suppress the original VK from applications.

### Macro read/edit and custom outputs

We have **not** decoded the individual `0x0A` event bytes into timing and key events, developed a general macro slot manager, verified a live macro read command, or tested arbitrary macro output usages such as F13 or vendor-defined reports.

HID keyboard usage F13 is `0x68` (Windows VK_F13 `0x7C`) but whether the **K758** firmware accepts that option or produces a held F13 versus a macro tap is **not verified**. A macro that synthesizes F13 is still a **keyboard signal**, not a native KHID event.

### Full profiles and persistence

M1-M4 **exist** as active selectable hardware banks. **This does not prove** independent validated backups, known complete macro tables, or safe arbitrary full-profile writes for each bank. Captured OEM profiles are historical images, not an on-demand EEPROM snapshot.

Our desired first-detection snapshot policy (fingerprint + USB port attachment, before any change) is **not yet fully implemented**: it must include all retrievable onboard state, mark unreadable macro banks explicitly, and never claim completeness when any storage domain is unknown.

### Input suppression and output

No reliable K758 runtime-to-KHID physical edge generator, Windows original-key suppression, software macro engine, or loop-safe output injection has yet been demonstrated in this standalone driver. Recording a VK and injecting a second VK without suppression would cause **both** actions, not genuine remapping.

## Commands that are safe to run now

From repository root on Windows after building with `cargo build --release`, with `K758RGB.exe` completely closed:

```powershell
# Read-only diagnostic: active hardware bank, lighting and keymap views
.\target\release\k758_profile_audit.exe

# Offline byte/transaction check; no USB writes
.\target\release\k758-protocol-lab.exe .\fixtures\m1_D_A_to_D_PREVIEW_only.json --dry-run

# K758 M1 live read-only verification; expected to succeed after restoration
.\target\release\k758-protocol-lab.exe .\fixtures\m1_D_A_to_D_PREVIEW_only.json --verify-restored
```

**Do NOT casually run:** `--select-m1` (changes hardware bank) or `--apply-m1-d --confirm-complete-m1-overwrite` (replays a historical **complete** M1 macro/keymap transaction). The latter can restore **old macro contents** if those have changed since the OEM capture.

## Priority next experiments, in order of safety

1. **Read-only** record `MI_00` keyboard events and `MI_01` vendor events around W's macro **with the OEM app closed**. Log source collection, timestamps, profile, physical press/release observations, and unexpected characters. Protect the resulting raw input logs.
2. Establish whether the K758 exposes a *unique vendor event* for a physical macro key. If it is only a press notification, model it as a KHID **trigger**, not an invented down/up hold.
3. Decode the historical two `0x0A` packets **offline**. Correlate a minimal OEM macro edit against captured before/after packets to infer event encoding, no arbitrary HID writes.
4. Factor common Rust packet/checksum/response logic into a tested library. Preserve exact M1 readback/restore regression vectors.
5. Implement a deterministic software `source -> KHID -> profile -> action` pipeline with mocked input, then real read-only K758 input.
6. Design a Windows suppression strategy only if physical keys also leak ordinary keyboard input; Raw Input cannot suppress them.
7. Only consider live write support for more profiles or custom outputs after **separate verifiable backups** and explicit approval.

**Strong invariant:** hardware configuration must never be changed on discovery, automatically on KHID translation, or merely to render the GUI. With experimental writes, fail closed on unknown device identity, unknown profile, unknown macro storage, or mismatched preflight state.
